  - 동명이인은 이메일이 식별자이므로 자동 해소 (별도 보조 입력 불필요)

### 0.1 인증 관련 결정·미정

**확정 (2026-05-13)**
- ~~도메인 화이트리스트~~ → **강제하지 않음**. 사내 전용은 배포/공유 범위로만 통제 (URL 비공개 등)
- ~~이메일 인증(확인 메일)~~ → **제외**. 가입 즉시 사용 가능 ("간단하게" 결정 반영)
- 자유 가입 채택 — 관리자 초대 방식은 채택하지 않음 (기본값)

**확정 추가 (2026-05-13)**
- **패스워드 정책**: 최소 8자 + 영문·숫자 조합 (특수문자 강제 X, 만료 없음)
- **패스워드 재설정**: MVP 범위에서 **제외**. 필요 시 관리자가 DB 직접 처리. F1 화면에 "비밀번호 잊었나요?" 링크 노출 X

## 1. 일일 파티 메뉴 추천 대시보드

> 오늘 어떤 메뉴/파티가 있을지 한눈에 보고, 클릭 한 번으로 파티 생성까지 이어지는 진입 화면.

### 1.1 추천 / 빠른 생성
- **선택으로 바로 생성**: 추천된 메뉴 클릭 → 즉시 파티 생성 플로우 진입
- **추천 데이터 소스**: 외부 크롤링 X → **자체 파티 생성 히스토리 기반**

### 1.2 음식점 만족도 리스트
- 그동안 누적된 평가를 기반으로 음식점을 만족도순으로 노출

### 1.3 음식점 평가 (피드백 항목 예시)
- 평소 대기시간이 너무 길다
- 어떤 메뉴는 맛이 없다 (메뉴 단위 평가)
- 음식점 메뉴판 (이미지/링크 첨부)

### 1.4 미정/검토
- ~~추천 정렬 기준~~ → **최근성 + 랜덤** 확정. 최근 N일 내 다녀온 식당은 후순위, 나머지에서 랜덤 노출. N값은 구현 시 결정 (초안 7일)
- ~~평가는 별점인지 태그형 체크인지~~ → **별점 + 태그 조합**. 메뉴(M2)는 별점 중심, 식당(M1)은 태그 중심으로 표면 분리 (UI에 §3.4.1 메뉴 평가 분리 결정 반영)
- ~~평가 주체~~ → **다녀온 파티 참여자만**. 파티 종료 후 해당 식당·메뉴에 대해서만 평가 권한 부여. 노이즈 차단·신뢰도 확보
- "어떤 메뉴는 맛이 없다"는 음식점 단위가 아닌 메뉴 단위라는 점 → 메뉴 평가 스키마 분리 필요 (§3.4.1과 동일 결정)

## 2. 파티 (Party)

> **정의**: 같이 갈 사람들을 모으기 위해 생성하는 방. **인스턴스성** (1회성 이벤트).

### 2.1 파티 생성 항목
- **파티 명**
- **출발 시간** (몇 시 출발)
- **참여 제한 시간** (참여 신청 마감 시각)
- **모이는 장소**
- **메뉴 선정**
- **평균 가격대**
- **인원 모델** (MVP: **선착순만**)
  - 정원 입력 (2명 이상) + 선착순 합류
  - 랜덤 모집·지정 인원 모드는 MVP 이후 (현재 §2.3에서 제외)
- **파티 규칙** (자유 기재, 예시)
  - 모임 내내 대화하지 않는다
  - 셀프코너는 자기가 알아서 한다
- **추가 스케줄** (옵션)
  - 커피숍
  - 산책코스
- **음식점 정보**
  - 음식점 URL
  - 지도 표시 기능

### 2.2 파티 목록 화면
- 당일 생성된 파티 리스트 노출

### 2.3 미정/검토
- ~~"인원수 제한(선착순)" vs "모임 인원(생성자 직접 입력 / 랜덤 모집 / 지정 인원)" 관계 정리 필요~~ → **MVP는 선착순만**. 랜덤·지정은 이후 에디션
- ~~정원 미달 시 처리~~ → **그대로 진행 (2명 이상이면 OK)**. 제한 시각 도달해도 자동 무산 없음. N3 자동 무산 알림도 MVP에서 제외 (§C2 보류)
- 파티 취소·해체 권한 / 조건
- 파티장 vs 일반 참여자 권한 구분
- ~~동명이인 처리 방식~~ → §0 이메일 식별 도입으로 해소 (UI상 표시명 중복은 별도 처리)
- 파티 목록 정렬/필터 (출발시간 / 카테고리 / 잔여 인원 / 가격대)

## 3. 히스토리

> 종료된 파티 데이터를 누적해서 추천·재사용에 활용.

### 3.1 재파티 생성
- 이전 히스토리에서 한 번에 동일 조건으로 **재파티 생성** 가능

### 3.2 식당 정보 스키마
- 이름 / 주소
- 카테고리1: 한 / 중 / 일 / 양
- 카테고리2: 세부 메뉴 (김치찌개 / 파스타 등)
- 대기도: 심각 / 중간 / 한산
- 예약 필수 여부
- **해시태그** (자유 태깅 + 검색용)
  - 식당에 자유롭게 해시태그를 달 수 있음
  - 예: `#혼밥가능` `#룸있음` `#가성비` `#회식하기좋음` `#매운맛주의` `#사장님친절` `#주차가능` `#비올때` `#든든한한끼`
  - 카테고리1·2가 *고정 분류* 라면, 해시태그는 *자유 라벨* 역할
  - 나중에 해시태그로 식당/파티 검색 가능 (예: `#가성비` 클릭 → 해당 태그 식당 리스트)

### 3.3 추천 메뉴 (식당별)
- 먹었던 메뉴를 입력해 데이터 누적
- 항목: 메뉴명, 가격

### 3.4 데이터·추천 강화
> 누적된 히스토리를 단순 조회용으로만 두지 않고, 대시보드 추천 품질을 끌어올리는 데 활용.

- **3.4.1 메뉴 단위 평가 분리**
  - "식당은 좋은데 ○○메뉴는 별로"를 표현 가능하도록 *식당 평가* 와 *메뉴 평가* 두 단으로 분리
  - 메뉴 평가가 식당 평점에 묻히지 않게 함
- **3.4.2 만족도 가중치 추천**
  - 단순 빈도순이 아니라 (최근성 × 만족도 × 참여인원) 같은 가중치 적용
  - 자주 갔지만 평이 낮은 곳은 자연스럽게 후순위로
- **3.4.3 날씨/계절 추천**
  - 비 오는 날엔 가까운 식당, 더운 날엔 시원한 메뉴, 추운 날엔 국물 메뉴
  - 가벼운 룰 기반만으로 시작 가능
- **3.4.4 "오늘 안 먹은 카테고리" 가중치**
  - 어제·최근 며칠 다녀온 카테고리는 후순위, 안 먹은 카테고리 우선 노출
  - 개인별 최근 이력 / 회사 전체 최근 이력 두 단으로 분리 가능
- (※ 검토: 가중치 식은 후속 단계에서 조정 — 데이터 쌓인 뒤 튜닝)

### 3.5 해시태그 검색
- **검색 진입점**
  - 식당 상세에서 태그 클릭 → 동일 태그 식당 목록
  - 대시보드/파티 목록에서 태그 검색바 또는 인기 태그 칩
  - 파티 생성 화면에서 태그로 식당 빠르게 찾기
- **자동완성**: 기존 태그 풀에서 추천 (오타·난립 방지)
- **인기/추천 태그**: 최근 많이 쓰인 태그 노출

### 3.6 미정/검토
- 대기도 입력 주체 (파티 종료 후 참여자 평가?)
- 메뉴 가격 변동 추적
- 카테고리 자동 분류 가능 여부
- **해시태그 운영**
  - 태그를 누가 달 수 있나? (파티 참여자만 / 누구나)
  - 태그 정규화 — 동의어 처리(`#혼밥` ↔ `#혼밥가능`), 띄어쓰기·대소문자
  - 부적절·중복 태그 정리 권한 (관리자?)
  - 태그 삭제/수정 권한
  - 태그 글자수 제한, 1개 식당당 태그 개수 상한
  - 메뉴 단위 태그도 둘지 (예: `#매운맛` 메뉴 자체에)

## 5. 특수 모드 & 게이미피케이션

> 핵심 파티 기능 외에 사용 경험을 풍부하게 만드는 보조 모드/장치들.

### 5.1 사일런트 런치 (Silent Lunch)
- 파티 생성 시 선택할 수 있는 **모드 프리셋**
- "모임 내내 대화하지 않는다" 규칙이 기본으로 적용됨 (책·노트북 들고 오는 사람용)
- 파티 카드에 🤫 아이콘 등 시각적 마커 노출
- (※ 검토: §2.1 파티 규칙 자유 기재와의 관계 — 사일런트 런치는 *프리셋 토글*, 일반 규칙란은 *자유 텍스트*)

### 5.2 혼밥 매칭 (Solo Lunch Mode)
- 같이 가지는 않지만 **"지금 혼밥 중"** 상태를 표시하는 별도 모드 (파티 아님)
- 같은 식당에 다른 혼밥러가 있으면 선택적 알림 ("같은 가게에 ○○님도 혼밥 중")
- 인사·합석 의무 없음 — 단순 정보 표시가 기본
- 옵션: 위치 공개 범위 (식당만 / 식당+자리 / 비공개)
- (※ 검토: 프라이버시 — 혼밥 표시를 자동 노출할지, 본인이 토글해야 보이게 할지)

### 5.3 AI 잔소리 코치
- 대시보드 상단에 한 줄 코멘트로 가벼운 참견
- 예: "최근 일주일 전부 한식이었어요. 오늘은 양식 어떠세요?"
- 예: "이번 주에 ○○식당 3번 가셨네요, 슬슬 다른 곳도?"
- 데이터 소스: §3.4.4 "오늘 안 먹은 카테고리" 가중치 로직 재활용
- 사용자별 **끄기 가능** (잔소리 싫어하는 사람용)

### 5.4 월간 뱃지 자동 부여
- 매월 말 히스토리 통계를 기반으로 자동 산정
- 기본 뱃지 후보
  - 🍱 **미식가**: 가장 다양한 카테고리를 섭렵한 사람
  - 🗺️ **모험가**: 처음 가본 식당이 가장 많은 사람
  - 👑 **호스트왕**: 파티 주최 횟수 1위
  - 👻 **노쇼왕**: 노쇼 횟수 최다 (조용히 카운트만, §C1 노쇼 카운터와 연계)
- 프로필/파티 카드 옆에 작은 뱃지 노출
- (※ 검토: 추가 후보 — 단골왕(같은 식당 최다), 균형왕(카테고리 고르게), 모임러(파티 참여 횟수))
- (※ 검토: 노쇼왕 같은 부정적 뱃지를 공개로 둘지, 본인만 볼 수 있게 할지)

## 6. 비기능 요구사항

### 6.1 반응형 디자인 (개발 막바지에 적용)
- **적용 시점**: 핵심 기능 구현 완료 후 마지막 단계에서 반응형 대응
- **타겟**: 데스크탑 / 태블릿 / 모바일 (브라우저 기반 가정)
- **원칙**
  - 기능 개발 단계에서는 데스크탑 기준 우선 진행
  - 마크업·스타일은 처음부터 반응형 전환을 깨뜨리지 않게 작성 (고정 px 남발 금지, flex/grid 기반)
  - 막바지에 브레이크포인트 정의 → 모바일 레이아웃 정리
- (※ 검토 필요: 모바일 우선 사용처가 많을지 — 점심 직전 폰으로 파티 합류하는 시나리오라면 모바일 UX 비중 ↑)

### 6.2 기타 (추후 확정)
- 플랫폼: 웹 / 네이티브 앱 여부
- ~~사용 범위: 사내 전용 / 공개 / 특정 그룹~~ → **사내 전용 확정** (§0 인증 결정과 함께)
- 데이터 보관 기간 (특히 히스토리)
- 동시 접속 규모

## 7. 추가 제안 (검토용)

> 요구사항을 보며 자연스럽게 떠오른 후속 기능 후보. 채택 여부는 미정.
> (※ 기존 A 데이터·추천 강화 그룹은 §3.4 히스토리 하위로 이동)

### B. 사용성·참여 경험
- **B1. 즐겨찾기 식당 / 즐겨찾기 메뉴**: 자주 가는 곳을 핀해두면 파티 생성 속도↑.
- **B2. 식이 제한 태그**: 채식 / 알러지 / 매운 거 못 먹음 등을 파티에 표시.
- **B3. 멤버 코멘트(공지)**: 파티장이 "11:55에 1층 로비 집결" 같은 공지를 띄울 수 있는 한 줄 영역.
- **B4. 출발 임박 알림**: 출발 5–10분 전 자동 알림 (브라우저/슬랙).
- **B5. 한줄 후기**: 파티 종료 후 한 줄씩 남기면 그게 히스토리·추천에 반영.

### C. 신뢰성·운영
- **C1. 노쇼 카운터**: 참여 확정 후 안 온 횟수를 카운트(징벌 X, 정보 제공). 실명 베이스라 자연스럽게 자정 작용.
- ~~**C2. 정원 미달 자동 처리 정책**~~ → **MVP 제외**. §2.3에서 "2명 이상이면 그대로 진행" 결정으로 자동 무산 정책 없음
- **C3. 중복 참여 방지**: 같은 시간대 다른 파티에 이미 참여 중이면 입장 차단 또는 경고.
- **C4. 파티장 위임**: 파티장이 사정으로 못 가게 되면 다른 참여자에게 권한 이양.

### D. 확장성
- **D1. 팀/그룹 단위 통계**: "우리 팀이 이번 달 제일 많이 간 식당 TOP 5" 같은 위클리/먼슬리 리포트.
- **D2. 캘린더 연동**: 참여 확정 시 본인 캘린더에 점심 일정 등록.
- **D3. 영수증/더치페이 메모**: 파티 종료 후 결제자/분담 메모 저장 (정산 도구가 아니라 기록용).

### E. 우선순위 제안 (개인 의견) — *과거 안*
- **MVP 후보**: 0(기본) + 2(파티 생성·목록) + 3.1(재파티 생성) + 4.1(지도) + B3(공지) + B4(알림)
- **차순위**: 1(대시보드 추천) + 1.2/1.3(평가) + 3.2/3.3(식당·메뉴 히스토리 스키마) + 3.4.1(메뉴 평가 분리)
